# Issue #82｜クレジットノートの下書き作成サービス

2026-11-05 / Draft専用・公開APIなし・Staging/Production未適用

## 動作

- 売り手テナントのACTIVEなOWNER/ADMINだけが、元の発行済み・入金済みInvoiceに対してクレジットノート**下書き**を作成できる。
- 元の企業間返品申請、売り手受注、買い手発注、企業間接続の状態を確認。元売り手OrderがそのInvoiceOrderに含まれる必要がある。
- 買い手PurchaseOrder → TradingConnection → B2BReturnRequest → B2BReturnItem（ID順） → 元Invoice の順にロックし、最新の物理INSPECTIONイベントと既存のCreditNote下書きの割当数量を再集計する。
- 返送のみでは金額調整しない。INSPECTIONで現物確認した数量から、先行するすべての下書きの割当数を差し引いた残量を上限とする。
- クライアント側UUIDを元に企業内で一意の下書き番号を作成。同じ担当者・企業・元請求書・返品申請・通貨・明細・数量で再送したら同一結果を返す。別内容なら拒否する。
- ヘッダーと明細はSerializableの一つのDBトランザクション。部分書き込みは残さない。
- **金額欄はすべてNULL**。税額配賦、通貨の補助単位、端数、他の請求伝票との関係、元請求書の既払金との整合が確定していないため、返金額やクレジット金額を算出しない。
- Draft DB側のCHECKとtriggerにより、DRAFT以外の状態保存・元請求書の改変・明細数量変更・不正な企業境界を禁止する。

## テスト項目

隔離PostgreSQLにて、正常な下書き、二重送信の冪等性、同じキーで異なる数量の拒否、
売り手STAFFの操作拒否、買い手企業へのなりすまし拒否、実検品残1個を2つの同時処理が奪い合うケース（成功1、失敗1）、Invoiceと入出庫台帳が変わらないことを検証する。
