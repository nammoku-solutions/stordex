# Issue #82 — B2B出荷後返品の基盤（2026-11-04）

> 状態: **設計と隔離PostgreSQLテストのみ。DB変更はStaging・Production未適用。**
>
> この文書/PRだけでは返品・返金・在庫戻しを実行できない。必要な取引台帳と
> 在庫・税額・支払処理が未実装のため、返品UIの操作ボタンも公開しない。

## 先行投入した読み取り専用のガード（PR #106）

- 企業間受注が `ACCEPTED`、売り手受注が `SHIPPED/COMPLETED`、
  買い手仕入発注が `RECEIVED`、接続が `ACTIVE` の時だけ
  元の入荷数を「参考情報」として表示する。
- 対応する買い手発注明細ID、数量、単位を再照合する。
- 入荷数は**返品可能残数ではない**。既存/過去の返品、棚卸、現品状態、
  在庫所在地、請求/返金残額を反映していない。
- 画面は閲覧のみで、申請作成や在庫移動・返金は実行しない。

## 先に必要な売り手側明細の正確な対応付け

企業間発注明細は現在 `sourcePurchaseOrderItemId` を保持するが、
売り手が企業間発注を承認した時に作られる
`OrderItem` のIDを直接記録していない。

商品名、数量、単価、配列順による照合は危険。
同じ商品/金額の複数行、複数SKUを売り手が別商品へマッピングした場合に
返品の数量や在庫が誤った行へ紐づき得る。

この後続Draftでは、`IntercompanyOrderItem.sellerOrderItemId` を
**NULL許容・一意**に追加し、新しい企業間受注の承認時には
売り手OrderItem IDを明示生成して同一トランザクションで保存する。

PostgreSQLの専用トリガーは、対応先OrderItemがその企業間取引の
`sellerOrderId` と `sellerTenantId` に所属することを検査し、
一度紐づけた対応IDを上書きしない。

既存の企業間受注（過去に承認された明細）の対応欄は `NULL` のままにし、
**類推による自動バックフィルを禁止**する。必要な過去分は監査・人手承認と
独立した根拠のある手続きで扱う。

## 今後の業務フロー（別PRに分割）

1. 買い手が実入荷・過去返品と突合し、明細ごとに返品申請
2. 売り手が承認/部分承認/否認（承認だけでは在庫を変更しない）
3. 現物返送確定で買い手の在庫を1回だけ減算（専用一意イベント）
4. 売り手の検品で良品のみ1回だけ増算、破損/廃棄は隔離記録
5. 売上請求書との税額・返金・CreditNoteを関連付け、元伝票は保持

返送上限は仕入発注の**実入荷数**と対応する売り手の実出荷数の小さい方、
さらに先行の返品/予約・実在庫を考慮して制御する。
一部返品、複数回返品、同時申請の競合、接続失効/テナント境界、支払の差異を検証する。
