# Stordex 登録メール通知の実装計画 — Issue #110

状態：**イベント定義・テストのみ。メール送信なし。DB変更なし。**

## 通知するタイミング

| ビジネスイベント | 通知を受ける会社 | 参照先 |
|---|---|---|
| 自社の新規受注が登録された | 受注企業 | 自社受注詳細 |
| 企業間発注が受信トレイに届いた | 売り手 | 企業間受注トレイ |
| 売り手が企業間発注を承認した | 買い手 | 自社仕入発注詳細 |
| 売り手が企業間発注を否認した | 買い手 | 自社仕入発注詳細 |
| 売り手が出荷済みにした | 買い手 | 自社仕入発注詳細 |
| 買い手が入荷を確定した | 売り手 | 自社受注詳細 |

今後、出荷取消・返品申請・返品承認・クレジットノートなどが実装されたらイベントを追加する。メール内に商品名・金額・取引先名・顧客情報を直接載せず、認証済みのStordex画面で確認する。

## 完了した準備

`src/lib/notification-event-contract.ts` では、業務イベント種別から通知先**テナント**と必要なログイン後の画面パス、文言、決定的なSHA-256重複排除キーを生成する。第三者のテナントを直接指定するパラメータは提供しない。イベントIDはUUIDを要求し、受注・発注IDはパス文字を制限する。

この関数は完全に読み取り専用で、登録メールアドレス・送信事業者・キュー・DBにはアクセスしない。関数が返した内容だけではメールを送信できない。

## 未実装の必須項目（将来）

1. **Domain event / Outbox**：確定した状態変更と同一DBトランザクション内でイベントを書き込み、受信企業ID・イベントID・伝票の状態変更版を保存。一意キーで重複を防止する。状態変更がROLLBACKした場合はイベントを生成しない。
2. **受信者抽出**：配送時に対象テナントの有効なユーザーを認証基盤の `User` から取得し、権限・メール認証状態・個人通知設定・配信停止やバウンス情報を確認する。企業テナントに存在しないメールアドレスへ送らない。
3. **メール送信ワーカー**：送信プロバイダをシークレット設定、SPF/DKIM/DMARC、サンドボックステスト送信、指数バックオフ・レート制限・DLQ・送信試行と障害監査。送信で業務更新を失敗させない。
4. **管理UI**：会社管理者と個人の通知ON/OFF、送信先確認、配信失敗表示。法的に必要な通知と任意通知の区分を定義する。
5. **安全性**：テナント間情報漏洩、クリック先認証、繰り返しクリック・同時ステータス変更時の二重メール、接続失効、送信者メール認証、配信停止、業務更新前の誤送信を統合テストする。
6. **UAT**：Stagingでは許可したテスト受信先だけを使用。実利用者への無断メールは送信しない。操作マニュアル更新と全コードのCodex Astraレビュー後にProductionを判断する。

## 注意点

`dedupeKey` を計算できることと、メールの**exactly-once delivery**を保証することは異なる。ワーカーは送信結果取得失敗時の再送やプロバイダ側重複も考慮し、outboxとprovider idempotency機能を使用して可能な限り実質的な重複を防止する。

この計画は本番通知の有効化を承認するものではない。
