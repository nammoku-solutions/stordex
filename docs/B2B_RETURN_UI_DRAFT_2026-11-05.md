# Issue #82 — 返品申請・売り手審査の画面 Draft（2026-11-05）

**状態：Draft PRのみ。Staging/Production未適用、機能フラグ初期値OFF。**
依存：#107（売り手明細ID）→ #112（返品DBモデル）→ #115（取引制御付き申請・審査サービス）→ このUI。

## 画面導線

- 買い手の仕入発注詳細：企業間取引に紐づいた発注には「返品を申請」「申請履歴」を表示
- `/returns/new?purchaseOrderId=...`：売り手の出荷・買い手入荷確定・ACTIVE接続、実入荷数、売り手との正確な明細対応IDを読んで申請入力を表示
- `/returns`：ログイン企業が買い手または売り手の返品申請だけを一覧表示
- `/returns/[id]`：元の明細・申請数・審査内容の詳細。売り手OWNER/ADMINのみ、未審査の申請で承認数量と理由を入力できる
- 売り手の受注詳細：企業間注文の場合、返品申請一覧への導線を表示

## 有効化条件

全画面およびServer Actionsは `STORDEX_B2B_RETURNS_ENABLED=true` が設定された時のみ使用できる。
**Staging/Productionにこの環境変数を今設定してはならない。**
未設定なら `/returns...` は404となり、Actionは無効メッセージを返す。

前提のPostgreSQL migrationsは Staging で未適用。新しいテーブルが存在しない環境で、フラグを有効化してはいけない。

## セキュリティと業務上の制約

- 画面の表示とServer Actionsの**双方**でログイン企業・権限を確認する。
- 入力した hidden IDや数量を信頼せず、申請・審査サービス内のSerializableトランザクションで元企業/売り手出荷/買い手入荷/対応明細/過去申請上限を再検証する。
- 既存申請との数量競合を考慮した申請を行い、繰り返し送信は同一 UUID により同じ申請に帰着させる。違う内容での再利用は拒否。
- 承認・一部承認・否認は卖り手OWNER/ADMINのみ。一部承認・否認は理由が必須。
- 提出時のエラーメッセージは赤い `role=alert` に表示し、内部DBエラー・個人情報・SQLは表示しない。
- 返品申請と売り手審査の完了時点では**在庫・配送・請求・返金を一切変更しない**。返送、検品、クレジットノートは将来の別工程。
- 画面で表示する「入荷済み数量」は過去の累積入荷数であり、返品可能残数ではない。申請時に必ず再検証。
