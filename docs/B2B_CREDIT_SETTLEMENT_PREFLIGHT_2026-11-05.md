# Issue #82 — CreditNote 精算方法の分離と送金停止ゲート（2026-11-05）

本変更は**計画・整合性検証のみ**で、DBへの書込み・請求残高更新・実際の返金・送金・通知は一切行わない。現在のDraftクレジットノートDB (#121) は DRAFT 以外の状態への遷移をCHECK/Triggerで禁止しているため、ここで検証するISSUED状態のCreditNoteは**まだ実運用で発生しない**。

## 承認の段階を混同しない

1. **返品事実の確定**：売り手が申請を承認し、買い手が現品返送し、売り手が検品した。実績は返品イベントと在庫台帳に記録。
2. **金額案の照合**：元Invoice、元の注文、消費税・GST等の税計算単位、通貨の最小単位、税込/税抜、端数、過去調整の全額・数量と照合。下書き・レビューでは債権や現金に触れない。
3. **正式CreditNoteの発行**：別途承認された税額・書類発行番号・日付・権限・法的要件で確定。元請求書の税・合計は上書きしない。
4. **精算方法の選択**：次の２種類は完全に異なる会計イベントとして扱う。
   - **REFUND**：実際に入金済みの対象金額を、確認済みの支払元へ返す。PAIDの請求書でも「返金可能額」を実際の入金・既返金履歴から検証する。PAIDだけで自動返金は禁止。
   - **INVOICE_OFFSET**：売り手が回収する予定の**未回収の債権**を、そのCreditNoteの残高で相殺する。発行済みInvoiceが存在するだけでは未回収残高は保証できない。相殺対象の請求書、顧客、企業、通貨、残債を認証し、台帳で確認する。
5. **計上済み処理と照合**：部分返金・部分相殺を跨いで全settlementの総和がCreditNoteの発行金額を超えないようにする。相殺と返金の二重計上を許可しない。

## 将来DB設計上の要件

- `B2BCreditSettlement`などの**append-only**台帳：sellerTenantId、creditNoteId、kind、targetPaymentId / targetInvoiceId、amountMinor、currency、domainEventUUID、actor、状態、作成日時、audit trail。
- `(sellerTenantId, domainEventUUID)` で一意性を保証。同じキー・同じpayloadなら結果再利用、異なるpayloadなら拒否。
- 操作と会計台帳反映を同一Serializableトランザクションにする。外部の銀行送金・決済APIへのアクセスはDB COMMIT外のOutbox/Workerで、重複実行と失敗に備える。
- 返金は回収済み支払イベントの**未返金額**を、相殺は該当未回収債権の**未相殺残高**を各々ロック中に検証。CreditNote残高と元invoice残高の両方から二重取りを防ぐ。
- 販売側・購入側の自社テナント権限、顧客・通貨・相殺対象の所有関係を必ずDBから再取得。クライアントが送るフラグや対象IDは信用しない。
- 同時実行、再送、タイムアウト、返金プロバイダ重複、複数Invoiceへの分割相殺、取消・返金不能・費用負担・現金引当が不足した場合を個別の統合テストで扱う。
- 税務・会計ルールと通貨の最小単位は国ごとに確認が必要。一般的なJPN/AUの規則を推測したまま税額を自動計算しない。

## 現在できること

`src/lib/b2b-credit-settlement-preflight.ts` は、処理種別・発行済CreditNote・元請求書状態・金額残高・各種照合の完了を前提に、提案額の上限、返金可能な入金額と相殺可能な債権残高を**別々に検証**する。

返り値は常に `MANUAL_SETTLEMENT_REVIEW_REQUIRED`。claimKeyとpayloadHashは将来の永続化のための識別子に過ぎず、現時点では二重送金防止を実現したとはみなさない。

## 本番リリース停止条件

Issue #109のNeon独立復元とマイグレーション単位の承認、#121以降のCreditNote発行・税配賦・決済台帳の監査、双方の企業のブラウザUAT、全機能完成後のCodex Astra全コード最終レビューPASSまで実際の精算は有効化しない。
