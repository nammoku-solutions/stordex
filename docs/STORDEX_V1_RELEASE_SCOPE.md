# Stordex v1 — 現場で使い始めるための最小範囲

2026-11-20。初回リリース方針と残作業の整理。これは本番デプロイ指示ではない。
以前の [Staging → Production 完成計画](STORDEX_STAGING_TO_PRODUCTION_COMPLETION_PLAN_2026-11-12.md)
は経緯として残し、初回の新機能範囲と順序はここを参照する。

## 現状

- 通常の受注、企業間の注文連携、出荷、入荷、在庫更新、通常の請求書はコード・Staging 検証実績がある。常備品の最低在庫、都度仕入品の余剰在庫、箱・パック、実数入荷と差異理由も実装済み。Issue #88 が開いていても、旧 PR #89 を一括で取り込まない。
- 企業間返品の申請・承認・返送・検品と、金額なし CreditNote 下書きの個別 Staging UAT は実施済み。個別 PASS と v1 組み合わせ UAT は別。CreditNote 下書きは現在 Vercel の Staging 専用ガードで、AWS 本番で使える状態とは扱わない。
- CSV は商品・得意先・仕入先・受注の取り込みと、必要な業務データの出力がある。過去の仕入発注・在庫移動は出力、事前検証や照合、CI での隔離リハーサルがあるが、運用画面から過去履歴を一括復元できるとは案内しない。
- 直前まで進めていた原本請求書 PDF 審査は Staging 専用で停止。Migration #12 は 2026-11-20 に Neon の Staging（`stordex-staging` / `staging` / `neondb`）に適用・照合済み。既存業務データは変化なし。適用済みSQLとPrisma schema・CIのソース整合はPR #187でStagingに反映・全CI PASS。PR #184は履歴としてクローズし、適用済み Staging に再適用・巻き戻しをしない。専用 AWS 検証ホストは立てず、PDF 機能は有効にしない。

## 優先順位

| 判定 | 機能 | リリース前にやること |
| --- | --- | --- |
| v1 必須 | 受注、仕入発注、出荷、実数入荷、企業間注文、請求書 | 現行の導線と状態表示を整え、買い手・売り手で通し検証。二重処理や在庫差異があれば修正。 |
| v1 必須 | 在庫・商品 | 常備品の不足と都度仕入品の余剰が見つかること、パック換算、発注数と実入荷数を混同しないことを確認。 |
| v1 必須 | 日常の導線 | よく使う操作を一階層目に置く。ホームは「次に何をするか」を優先。現在の状態、次の操作、入力エラーの直し方を日本語で伝える。 |
| v1 必須 | 基本 CSV（#62） | 商品・取引先・日常受注の取り込みと必要な出力を代表 CSV で再確認。初心者向けの手順には操作範囲と照合方法を記載。 |
| v1 推奨 | 返品・検品（#82） | 実物の戻りまでを扱う。返送、検品、在庫結果を両社で確認し、返金されるように見せない。正式発行・返金・相殺には進まない。 |
| 初回利用先に必要な場合のみ | 金額なし CreditNote 下書き、過去履歴の一括取り込み | 下書きが実際の現場作業に必要なら本番向け制御と意図した表示を別スライスで審査。履歴は初回利用先が持ち込むサンプルと必要範囲が決まってから対応。過去データから実在庫を勝手に増減させない。 |
| 後続／要望ベース | 受注・ステータス変更メール（#110）、FAX/OCR（#63）、外部連携・高度な集計 | 初回は受注・発注画面とホームの未処理表示を基準に運用。通知がないと注文を見落とす運用が判明した場合は新規受注通知だけを優先判断。 |
| 後続 | PDF 原本審査、正式 CreditNote、返金・相殺 | 各フローの必要性を確認。互いに依存する範囲は Staging の通し検証を済ませてから公開する。 |

既に使える見積・売上集計・設定を削除する必要はない。日常操作と同じ深さに並べず、必要なときに開く。権限・API の安全性を画面表示の有無に依存させない。

## 残りの順序と完了条件

1. **日常の導線** — メニューは主要6項目を直接表示し、その他は「商品・取引先」「見積・売上集計」「設定・CSV」に分ける。既存 URL と権限は維持。企業間返品はフォームが有効なときだけ追加する。ホーム上部の「よく使う操作」から、確認待ちの企業間受注、発注済み・未入荷の仕入発注、最低在庫を下回った常備品へ進める。未入荷の発注は出荷・到着済みを意味しない。商品が届いたら発注の詳細から実数を登録する。実機で、説明なしに操作を見つけられるか確認し、迷う箇所だけ直す。
2. **現場の通し試験** — Staging で受注 → 出荷 → 実数入荷 → 在庫と請求の照合を1シナリオ、別に返品・検品と代表 CSV を確認。合否だけでなく、どこで止まったか、何と読み違えたか、修正なしで進めたかを記録。税・在庫・権限・二重処理の不具合を優先し、要望だけで機能を増やさない。
3. **公開前レビュー** — 初回対象と保留を文書化。既知のマイグレーション履歴を照合し、アプリ全体を Codex Astra で機能・回帰・セキュリティ・性能・保守性レビュー。ブロッカーを修正し再レビューで PASS。（#87）
4. **AWS 東京での公開準備** — 本番 OIDC、DB マイグレーション、バックアップ／PITR、運用・切り戻しと初心者向け手順を確認。対象と手順を提示した上で、承認された本番リリースと公開後スモーク。（#4、#5）

大項目は4つ。新機能は既存フローの不足が現場確認で分かった分だけで、導線の仕上げと不具合修正が中心。初回利用先が過去データの全面復元を求めず、大きな修正がなければ、導線修正から最終レビュー・AWS公開準備まで概算1〜2週間。試験担当者・本番AWSの準備状況とレビュー指摘によって変わる。

メニューとホーム導線の変更はDBに書き込まず、新規マイグレーション、バックアップ／復元、AWSリソース作成、環境変数の変更を伴わない。

### ホーム導線のStaging確認

PCとスマホでログインし、次の3つを開く。リンク先を見るだけなら在庫や注文の状態を変更しない。

1. 「届いた注文を確認」から確認待ちの受信注文だけが見える。「すべての受信」で処理済みも見られる。
2. 「入荷待ちの発注を見る」から発注済み・未入荷だけが見える。発注番号から詳細に入り、現品が届いたときの実数登録を見つけられる。通し試験まで確定ボタンは押さない。
3. 「不足している在庫を見る」から在庫管理の最低在庫割れ欄に移る。現在庫と最低在庫を見分けられ、該当なしでも画面が開く。

## v1 UAT実施

手順・期待結果・書き込み前の注意は [v1 通し検証ガイド](STORDEX_V1_UAT_RUNBOOK.md) を参照する。2026-11-23 の読み取り専用照合では、企業間の確認待ち0件・入荷待ち0件・最低在庫割れ0件のため、実データでの通し試験には明示的に識別した新規テスト取引が必要。CI PASSと実画面でのUAT PASSは区別する。
